# 날씨 수집 내부 설계 검토안

## 원본과 상태

공통 동작은 [날씨 요구사항](../../weatherhood-specs/specs/weather-data/requirements.md), 응답 형식은 [날씨 API 계약](../../weatherhood-specs/contracts/weather-api.md)을 따른다. 아래는 기존 설계에서 옮긴 내부 처리 검토안이다. 서버 구현은 초기화되었으며 기능별 재설계와 실제 공급처 검증을 거쳐 구현한다. 기술 선택은 [서버 설계](architecture.md)를 따른다.

## 수집·저장

- 외부 호출과 무관한 격자·발표·대상 시각·자료 종류를 저장 키로 사용한다. 실황과 예보 원본을 덮어 섞지 않고 응답 조합 시 선택한다.
- 동일 격자·자료 종류·발표 시각의 동시 수집은 하나로 합친다. 페이지 단위 자료는 필요한 페이지를 모두 수집한 후 완전성을 판단한다.
- HTTP 성공뿐 아니라 기상청 본문 결과코드·날짜·격자·필수 항목·자료 수를 확인한다. 부분 페이지나 오류 응답으로 정상 저장본을 교체하지 않는다.
- 저장 자료가 충분하면 즉시 응답한다. 자료가 없는 첫 요청은 필요한 범위를 수집하며, 무제한 대기 대신 정해질 시간 예산 내에 계약된 부분 성공 또는 실패를 반환한다.
- 최근 조회 지역을 기상청 발표 주기에 맞춰 갱신한다. 전 지역 일괄 수집은 첫 구현 범위가 아니다. 발표 직후 미게시 시 기존 자료를 유지하고 호출 예산 안에서 재시도한다.
- 보존 기간은 수집 시각과 대상 시각을 모두 고려해 최소 48시간을 확보한다. 삭제 작업으로 오늘 타임라인이나 현재 유효한 미래 예보를 제거하지 않는다.
- 발표 지연, 갱신 실패, 오래된 자료, 일일 요청량·용량과 중복 수집 억제를 확인할 수 있게 기록한다. 인증키와 정확한 사용자 좌표는 로그에 남기지 않는다.

## 미정 사항

수집 시간 예산, 재시도 횟수·간격, 최근 지역 유지 기간, 보관 작업의 구체적인 SQL·인덱스·실행 주기와 공급처 인증키 전달 방식은 미정이다. API 동작에 영향을 주는 결정은 공통 계약에도 반영한다.

## 참고 및 검증

- 기존 공통 설계의 내부 수집·저장 내용을 원본 책임 기준에 따라 이동했다.
- 현재 서버 코드와 실제 기상청 인증 응답으로 검증하지 않았다.
