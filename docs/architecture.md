# 서버 기술 및 내부 설계

## 범위와 상태

서버 기술 선택의 원본이다. 기능 요구사항과 API 계약은 [공통 스펙](../../weatherhood-specs/README.md)을 따른다. 서버 구현은 초기화되었으며 아래 내용은 합의된 설계다. 프로젝트 생성·실행·통합 테스트는 아직 수행하지 않았다.

## 기술 선택

| 항목 | 결정과 이유 |
| --- | --- |
| 언어·프레임워크 | Java 25 LTS · Spring Boot 4.1.2를 기준안으로 사용한다. |
| 빌드 | Gradle + Wrapper. 정확한 버전은 프로젝트 생성 전에 호환성을 확인해 고정한다. |
| 실행·배포 | 하나의 Spring Boot 애플리케이션에서 API와 날씨 수집을 함께 실행한다. |
| 데이터베이스 | PostgreSQL. 지역·시간 기반 날씨 조회와 관계형 데이터 관리에 적합하고 기존 사용 경험을 활용할 수 있다. |
| 데이터 접근 | Spring Data JPA. JDBC 병행은 대량 저장이나 성능 문제를 확인한 뒤 검토한다. |
| 스키마 변경 | Flyway로 버전별 SQL을 Git에서 관리한다. 이미 적용한 변경 파일은 수정하지 않고 새 파일을 추가한다. JPA의 `ddl-auto`는 `validate`를 사용한다. |
| API 문서 | springdoc-openapi + Swagger UI. API 계약을 바탕으로 실제 직렬화 결과와 문서를 일치시킨다. |
| DB 통합 테스트 | Testcontainers로 개발 DB와 분리한 PostgreSQL 컨테이너를 실행하고 Flyway 적용 후 JPA 동작을 검증한다. |
| 순수 로직 테스트 | Spring·DB 없이 핵심 규칙을 검증한다. |

PostGIS·TimescaleDB는 도입하지 않는다. 공간 검색·대규모 시계열 처리 요구가 생기면 검토한다. Redis·메시지 큐·배치 프레임워크도 현재 선택하지 않았다.

## 코드 구조와 책임

기능별 패키지 안에 Controller·Service·Repository·DTO 등 역할을 구분한다. 초기 복잡도를 낮추면서 핵심 로직의 독립성과 테스트 가능성을 확보하기 위한 선택이다.

- Controller는 HTTP 요청·응답을 처리하고 Service는 기능의 흐름을 조율한다. Repository는 데이터 접근을 담당한다.
- 모든 Service에 인터페이스를 만들지 않는다. 외부 날씨 공급처처럼 분리가 필요한 경계에 인터페이스를 사용한다.
- 외부 연동 인터페이스는 우리 서비스의 타입을 사용한다. 공급처 응답과 앱에 반환하는 DTO를 구분한다.
- 예보 선택·유효성 판단 같은 핵심 규칙은 별도 객체로 분리해 외부 HTTP·DB 없이 테스트한다.
- 헥사고날 전체 구조를 도입하지 않는다. 실제 변경·테스트에서 확인한 문제를 근거로 구조를 개선한다.
- 세부 테이블·관계·인덱스는 기능·API 설계 이후 정한다. 빈 패키지나 업무 테이블을 미리 만들지 않는다.

## 테스트 데이터와 환경

Testcontainers의 임시 컨테이너와 데이터는 수명 종료 시 정리한다. 컨테이너를 여러 테스트에서 공유할 경우 테스트 사이의 데이터는 자동 초기화되지 않으므로 롤백·삭제 등으로 격리한다. 컨테이너 공유 범위와 초기화 방법은 테스트 구성 시 정한다.

PostgreSQL의 정확한 버전과 로컬 실행 방식은 미정이다. Docker Compose는 제안 단계다. 인증 제공자·세션 또는 토큰 방식, 보안 라이브러리 구성은 인증 설계 시 결정한다. 공급처 수집·재시도·보관 구현과 운영 수치는 기능 설계·공급처 검증 후 정한다.

## 참고 및 검증

- 근거: 서버 재설계 대화에서 합의한 기술 선택과 책임 분리, 문서 관리 기준.
- 현재 구현 검증 결과는 없다. 초기화 이전 서버의 테스트 기록은 Git 이력에서 확인하며 새 설계의 검증 증적으로 사용하지 않는다.
