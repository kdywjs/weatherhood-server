# 개발 테스트 서버 배포 설계

## 목적과 상태

외부 테스터가 앱에서 고정 HTTPS 주소로 접근할 수 있는 개발 테스트 환경을 구성한다. 기존 Ubuntu 미니 PC를 실행 호스트로 사용하고, `dev`에 병합한 서버 버전을 GitHub 제공 러너에서 SSH로 배포한다. 실제 사용자 대상 운영 환경(production)은 이번 범위에 포함하지 않는다.

이 문서는 개발 테스트 서버의 배포 기준과 검증 범위를 정리한다. 자동 배포는 구성했으며 실제 검증 결과와 보류 항목은 마지막에 기록한다. 서버 공통 기술 선택은 [서버 설계](architecture.md), 업무 동작과 API 계약은 [스펙 레포](../../weatherhood-specs/README.md)가 원본이다.

## 합의한 구성

| 항목 | 기준 |
| --- | --- |
| 호스트 | 기존 Ubuntu 미니 PC, x86_64 |
| 실행 관리 | Docker Compose로 Spring Boot·PostgreSQL 관리 |
| 외부 접속 | 보유 도메인의 고정 HTTPS 주소와 기존 Nginx Proxy Manager 사용. Cloudflare Tunnel은 사용하지 않음 |
| 접속 대상 | VPN 설치 없이 접속하는 외부 테스터 앱 |
| 배포 기준 | `dev` 병합 후 테스트·빌드 성공 시 별도 승인 없이 자동 배포 |
| 빌드·검증 | GitHub 제공 러너 |
| 이미지 저장 | GitHub Container Registry(GHCR), 비공개 이미지 |
| 정상 배포 이미지 보관 | 최근 정상 배포한 서로 다른 이미지 버전 3개 |
| 배포 실행 | GitHub 제공 러너 → SSH → 미니 PC의 제한된 배포 명령. self-hosted runner 설치 없음 |
| 실행 계정·환경 분리 | 배포 전용 SSH 자격증명·권한 사용. 기존 서비스와 폴더·Compose 프로젝트·DB 볼륨 분리 |
| 배포 중 가용성 | 서버 컨테이너 교체 중 짧은 서비스 중단 허용. 초기 구성은 무중단 배포를 요구하지 않음 |
| 수동 재배포·롤백 | GitHub Actions에서 기존 검증 이미지 선택. 롤백은 이전 정상 배포 버전 중 DB 호환 가능한 버전 선택 |
| 데이터 | 개발 PC의 로컬 DB와 분리한 테스트 서버 DB·영구 볼륨 |
| 구현 순서 | 배포 설계 → 도메인·HTTPS 라우팅 준비와 배포 기반 구현 병행 → 외부 접속 검증 |

API 주소는 `https://weatherhood-dev-api.ansandy.co.kr`, 문서 주소는 `https://weatherhood-dev-docs.ansandy.co.kr`로 확정한다. DNS·NPM 설정 완료와 서버 배포 후 외부 접속 검증을 구분한다.

## 접속과 실행 구조

배포 경로와 사용자 접속 경로를 분리한다.

```text
배포: GitHub 제공 러너 → SSH → 미니 PC 배포 명령 → GHCR 이미지 다운로드·컨테이너 교체
접속: 외부 앱 → 고정 HTTPS 도메인 → 기존 Nginx Proxy Manager → 미니 PC 서버 → PostgreSQL
```

- SSH는 배포 명령을 전달하는 통로다. 앱 요청을 전달하거나 HTTPS 인증서를 제공하는 역할은 아니다.
- 기존 Nginx Proxy Manager(NPM)로 HTTPS 요청을 받아 미니 PC의 Weatherhood 서버에 전달한다. Cloudflare Tunnel과 cloudflared는 구성하지 않는다.
- NPM은 미니 PC와 별도 장비에서 실행되는 기존 인스턴스를 사용한다. 실제 Weatherhood 도메인·인증서·라우팅·방화벽은 후속 연결 단계에서 확인하고 확정하며 다른 서비스의 라우팅을 유지한다.
- 기존 NPM 사용 시 서버 포트는 NPM이 접근 가능한 내부 인터페이스에 한정하고 충돌 없는 포트를 선택한다. DB는 Compose 내부에만 둔다. 외부 포워딩을 임의로 추가하지 않는다. 다른 장비의 NPM에서 미니 PC의 localhost나 Compose 서비스 이름으로 직접 연결할 수 있다고 가정하지 않는다.
- 앱 API와 외부 개발자용 Swagger UI·OpenAPI 명세를 제공한다. 관리·진단 상세 엔드포인트와 DB는 외부 차단한다. Swagger는 NPM Basic Auth로 보호한다.
- DNS 관리, HTTPS 프록시, Tunnel, 사용자 인증은 각각 다른 역할이다. Cloudflare DNS를 사용한다고 Tunnel이 필요한 것은 아니다. 초기 테스트 환경에는 앱 인증과 호출 제한을 적용하지 않는다. Swagger 보호는 유지한다.

## 개발 환경과 배포 환경 분리

- 개발 머신은 맥미니, 배포 호스트는 기존 Ubuntu 미니 PC다. 개발 체크아웃·IntelliJ·맥미니 로그인 상태와 무관하게 배포 서버가 실행돼야 한다.
- 배포 경로는 `/opt/weatherhood-dev`, Compose 프로젝트 이름은 `weatherhood-dev`로 한다. 기존 Midas·MoneySnap·Buzz 서비스의 Compose·네트워크·DB를 재사용하지 않고 전용 자원을 만든다.
- 배포 서버는 빌드된 이미지를 실행한다. 개발 소스 디렉터리를 마운트하지 않는다. 이미지는 `linux/amd64` 단일 플랫폼으로 빌드한다.
- SSH 관리 접속에 현재 사용하는 root 키를 Actions에 복사하지 않는다. 배포 계정·고정 명령·권한은 아래 기준에 따라 구현 전에 구체화한다.
- 초기 자원 상한: 서버 CPU 1·메모리 2GiB, PostgreSQL CPU 1·메모리 1GiB. 기존 서비스와 4 vCPU를 공유하므로 실제 부하·지연·메모리 사용량을 확인한다. 성능 보장은 아니다.
- 서버의 기존 애플리케이션·프록시·방화벽을 임의 변경하거나 호스트 전체 재시작·Docker prune·공유 볼륨 삭제를 수행하지 않는다. 변경 전에 관련 상태와 복구 방법을 확인한다.

## GitHub Actions 배포 흐름

1. PR에서는 GitHub 제공 러너로 테스트와 빌드를 수행한다. PostgreSQL 통합 테스트도 테스트 전용 환경에서 실행한다.
2. `dev` 병합으로 발생한 push에서 해당 커밋을 다시 검증하고 Docker 이미지를 만든다. 검증 실패 시 배포하지 않는다. 검증·이미지 게시 성공 후에는 별도 수동 승인 없이 배포한다.
3. 이미지를 GHCR에 업로드하고 커밋 SHA와 이미지 digest를 기록한다. 배포는 검증한 동일 digest를 지정하며 가변 `latest` 태그만으로 버전을 결정하지 않는다.
4. 검증·게시가 성공한 경우에만 GitHub 제공 러너가 배포 전용 SSH 인증으로 미니 PC의 고정 배포 명령을 실행한다. 명령은 검증한 이미지 digest를 내려받는다. SSH 연결·이미지 다운로드 실패 시 기존 서버를 유지한다.
5. 이전 배포 버전과 신규 버전을 기록한다. 새 이미지 다운로드를 완료한 뒤 기존 서버를 종료하고 새 서버 컨테이너를 실행한다. 이 교체 구간의 짧은 서비스 중단과 앱 요청 실패를 허용한다. 일반 서버 배포에서는 DB·기존 프록시을 유지한다.
6. DB 연결과 서버 준비 상태를 확인한다. 도메인 연결 후에는 외부 HTTPS 경로도 별도로 확인한다.
7. 성공한 이미지 digest·커밋·배포 시각·검증 결과를 남긴다. 실패는 성공으로 표시하지 않고 아래 복구 기준을 따른다.

배포는 환경당 하나씩 실행한다. 컨테이너 교체·마이그레이션 도중 새 실행이 기존 배포를 강제로 취소하지 않도록 한다. 늦게 끝난 이전 커밋의 빌드가 더 최신 배포를 덮지 않도록 배포 시작 시 대상 버전을 확인한다. 자동·수동 배포가 같은 Actions 동시 실행 그룹과 호스트 잠금을 공유한다. 실행 중 배포는 취소하지 않으며 대기 중 오래된 자동 배포는 시작 직전 제외한다. 잠금 구현은 Ubuntu에서 동작하는 방식으로 검증한다.

### 배포 성공 판단

- 새 서버 컨테이너 실행 후 요청 처리 준비 상태와 DB 연결을 5초마다 확인하고 최대 2분 대기한다. Flyway 마이그레이션과 JPA 스키마 검증도 통과해야 한다. 먼저 정상 상태가 확인되면 남은 시간을 기다리지 않는다.
- 2분 안에 정상 상태를 확인하지 못하거나 기동·마이그레이션·스키마 검증이 실패하면 배포 실패로 기록한다. 현재 DB와 호환되는 이전 정상 이미지가 있으면 복구를 시도하고 복구 결과도 확인한다. 호환성을 확인할 수 없으면 자동 롤백을 중단한다.
- 2분은 초기 기동 대기 기준이며 실제 기동 시간을 측정해 조정할 수 있다. 배포 전체나 장애 복구까지 2분 내에 끝난다는 보장은 아니다.
- 기상청·에어코리아·한국천문연구원 등 외부 공급처의 응답 성공은 서버 준비 상태의 필수 조건에 포함하지 않는다. 공급처 일시 장애만으로 정상 서버를 반복 배포·롤백하지 않는다.
- 도메인 연결 후 외부 HTTPS 접속도 추가 확인한다. 내부 서버는 정상인데 외부 접근만 실패하면 프록시·TLS·DNS·외부 연결 문제로 구분해 기록하고, 그 이유만으로 서버 이미지를 자동 롤백하지 않는다. 외부 접속 확인 전에는 외부 제공까지 정상이라고 표시하지 않는다.
- Spring Boot Actuator의 `/actuator/health/readiness`를 내부에서 사용하고 readinessState와 DB 검사를 명시적으로 포함한다. 개별 내부 점검 타임아웃은 3초이며 전체 2분 대기 예산을 넘기지 않는다. 기존 프로젝트에 Actuator 연동을 추가해야 한다.
- 외부 HTTPS 점검은 `/healthz`의 최소 상태 응답으로 수행하고 실제 날씨 조회 검증과 분리한다.

### 외부 상태 확인

- 외부 상태 확인 경로는 `GET /healthz`로 한다. 서버와 DB가 준비되면 HTTP 200, 준비되지 않았으면 HTTP 503을 반환한다.
- 응답에는 최소 상태만 제공하고 버전·DB 상세·오류 원인·외부 공급처 정보를 노출하지 않는다. 내부 readiness와 같은 서버·DB 기준을 사용한다.
- NPM에서 이 경로만 외부 상태 확인용으로 허용하며 Actuator 상세 경로는 공개하지 않는다.

### 수동 재배포와 롤백

- GitHub Actions의 수동 실행에서 기존에 검증·게시된 버전을 지정한다. 커밋 SHA에 연결된 이미지 digest로 실행하며 같은 소스를 다시 빌드하지 않는다.
- 재배포는 선택한 기존 이미지를 다시 실행하는 작업이다. 롤백은 이전 정상 배포 이력이 있는 버전으로 되돌리는 작업이다.
- 선택한 이미지의 존재·검증 이력과 현재 DB 스키마 호환성을 확인한다. 이미지가 없거나 호환성을 확인할 수 없으면 기존 서버를 교체하지 않고 중단한다. 초기 자동 롤백은 배포 전후 Flyway 적용 이력이 동일하고 실패·진행 중 마이그레이션이 없는 경우에만 허용한다. 적용 이력이 달라졌으면 자동 롤백을 중단한다. 수동 롤백도 대상 버전의 마지막 정상 배포 시점에 기록한 Flyway 적용 이력이 현재와 동일하고 실패·진행 중 마이그레이션이 없는 경우에만 허용한다. 이력이 다르거나 기록이 없으면 롤백을 중단하고 수정 버전을 배포한다.
- 수동 실행도 자동 배포와 같은 동시 실행 제어·정상 응답 검증·배포 이력 기록을 적용한다. 의도적으로 이전 버전을 선택한 롤백과 늦게 완료된 자동 배포를 구분한다.
- DB를 이전 상태로 되돌리거나 초기화하지 않는다. 실행자·선택 버전·결과를 기록한다.

### 이미지 보관

- 최근 정상 배포한 서로 다른 이미지 버전 3개를 보관한다. 같은 버전의 재배포는 별도 이미지 버전으로 세지 않는다.
- 현재 실행 버전과 직전 정상 버전이 삭제되지 않도록 배포 이력을 기준으로 정리한다. 진행 중인 배포·복구에서 사용하는 이미지는 정리 대상에서 제외한다.
- 정리된 버전은 기존 이미지 선택을 통한 재배포·롤백 대상에서 제외한다. 배포되지 않았거나 실패한 이미지는 생성 후 7일이 지나면 정리한다. 정상 배포 보관 대상 및 진행 중인 배포·복구 이미지는 이 정리에서도 제외한다.

## SSH 배포와 비밀 설정

- PR 검증·이미지 빌드·SSH 배포 작업 모두 GitHub 제공 러너에서 수행한다. 미니 PC나 개인 맥미니에 self-hosted runner를 등록하지 않는다. 서버 레포의 공개 여부는 변경하지 않는다.
- 배포 자격증명은 신뢰하는 dev 배포와 허용된 수동 실행에만 제공한다. PR 코드에 SSH 키를 제공하거나 pull_request_target에서 외부 PR 코드를 체크아웃해 실행하지 않는다. 배포 워크플로·스크립트 변경을 검토하며 CI 필수 검사도 연결한다.
- 배포 전용 SSH 키를 GitHub Actions의 비밀 설정으로 보관한다. 기존 root 관리 키를 재사용하지 않는다. 서버 계정은 `weatherhood-deploy`로 생성하고 authorized_keys의 고정 명령으로 Weatherhood 배포만 허용한다. 임의 셸·포트 포워딩·다른 프로젝트 제어 권한은 부여하지 않는다. 구체적인 제한 명령과 권한은 구현 시 검증한다.
- 호스트 키는 신뢰할 수 있는 기존 경로에서 확인해 고정하고 StrictHostKeyChecking을 유지한다. 배포 중 수신한 호스트 키를 검증 없이 신뢰하지 않는다. GitHub 러너에서 해당 SSH 엔드포인트로 실제 접속 가능한지도 검증한다.
- Docker 제어 권한은 다른 컨테이너·호스트에 영향을 줄 수 있다. 계정 분리나 docker 그룹 추가만으로 프로젝트 격리를 보장하지 않는다. 고정 배포 명령은 이미지 저장소·digest 형식·프로젝트·경로를 검증하고 임의 명령이나 Compose 파일을 입력으로 받지 않는다.
- GHCR은 비공개이며 게시에는 GITHUB_TOKEN의 packages: write, 배포에는 packages: read를 사용한다. 서버 레포 Actions에 패키지 접근 권한을 연결한다.
- 배포 작업의 단기 GITHUB_TOKEN을 암호화된 SSH 채널의 표준입력 등으로 전달하여 원격 docker login --password-stdin에 사용한다. 토큰을 원격 명령 문자열·프로세스 인자·로그·파일 산출물에 넣지 않는다. 고정 명령에 대한 입력 프로토콜은 구현 시 정한다.
- 원격 배포별 임시 DOCKER_CONFIG를 만들고 성공·실패 시 모두 정리한다. 기존 서비스의 Docker 인증 설정을 덮어쓰지 않는다. 비정상 종료 잔여물 정리와 동시 실행도 검증한다. GHCR용 장기 개인 토큰을 서버에 보관하지 않는다.
- 공급처 API 키·DB 비밀번호는 배포 폴더의 런타임 설정으로 주입하고 이미지·Git에서 제외한다. 소유자와 권한은 배포 계정 설계에 맞추고 파일 600·비밀 디렉터리 700을 사용한다.
- 로그는 Docker local 드라이버로 파일당 10MB·컨테이너당 3개 순환 보관한다. 비밀값·인증 URL은 기록하지 않는다. 실패 알림은 GitHub Actions 알림·실행 요약으로 제공하고 실제 수신을 검증한다.

## DB와 실패 복구

런타임 설정은 서버의 `/opt/weatherhood-dev/.env`에서 읽는다. root 소유·600 권한으로 API 키와 테스트 DB 비밀번호를 보관하며, 일반 배포가 이 파일을 교체하지 않는다. 변수 목록은 [runtime.env.example](../deploy/runtime.env.example)에 둔다. Docker 이미지에는 비밀값을 넣지 않는다.

GitHub `dev` 환경에는 `DEV_SSH_KEY`, `DEV_SSH_KNOWN_HOSTS`를 Secrets로, `DEV_SSH_HOST`, `DEV_SSH_PORT`를 Variables로 둔다. 호스트 키는 비밀이 아니지만 무결성을 유지해야 하므로 배포 설정으로 고정한다. 공통 설정은 [배포 Compose](../deploy/compose.yaml)에서 관리한다. 서버의 Compose·배포 스크립트는 root 소유이며 Actions가 임의로 덮어쓰지 못한다. 배포 기반 변경 시 관리 SSH로 검증된 파일을 별도 설치한다.

- PostgreSQL 데이터는 전용 영구 볼륨에 저장한다. 서버 컨테이너 교체나 배포 임시 디렉터리 정리가 DB 삭제로 이어지지 않아야 한다.
- Flyway 마이그레이션과 JPA 검증을 통과해야 신규 서버를 정상 배포로 처리한다. 실패 시 배포를 중단하고 원인을 확인한다.
- 신규 서버 준비 실패 시 이전 이미지로 복구를 시도하되, 현재 DB 스키마가 이전 버전과 호환되는 경우에만 수행한다. 이미지 롤백을 DB 롤백으로 간주하지 않는다.
- 비호환 DB 변경으로 이전 서버를 실행할 수 없으면 자동 롤백을 중단한다. 수동 수정 또는 DB 재구축 여부를 판단하며 배포 작업이 자동으로 볼륨을 삭제하지 않는다.
- 테스트 환경의 DB 백업은 수행하지 않는다. 데이터 유실 시 과거 상태 복원을 보장하지 않는다. 재구축 시 마이그레이션·기초 데이터 적재로 초기화한다. 영구 볼륨 유지와 백업은 구분한다.
- 단일 미니 PC 구성이다. 정전·네트워크 장애·OS 업데이트·재부팅 중 가용성을 보장하지 않는다. 테스트 서버의 일반 배포는 짧은 서비스 중단을 허용하며 무중단 배포를 요구하지 않는다. 실제 교체 중단 시간은 첫 배포 검증에서 측정한다. 정상 기동 대기 상한은 위 2분 기준을 적용하며 이를 중단 시간 보장으로 해석하지 않는다.

## 상시 실행 조건

- Ubuntu 부팅 시 Docker 서비스와 Weatherhood 컨테이너가 자동 시작되도록 구성한다. macOS 로그인이나 Actions 러너 상주 실행은 요구하지 않는다.
- 컨테이너 재시작 정책과 DB 준비 순서를 확인한다. 서버 재부팅 시 기존 서비스도 영향을 받으므로 실제 재부팅 검증은 별도 일정·승인 후 수행한다. 현재 Docker enabled 상태만으로 재부팅 복구를 검증했다고 표시하지 않는다.
- SSH 세션이나 GitHub Actions 작업 종료 후에도 서버가 유지돼야 한다. 재시작은 로컬에 있는 마지막 배포 이미지를 사용하며 GHCR 로그인부터 다시 요구하지 않는다.
- 디스크·로그·이미지 증가량을 관리한다. 정리 대상은 Weatherhood 소유 자원으로 한정하고 기존 서비스 이미지·볼륨을 보존한다.

## 외부 개발자 문서 제공

- 외부 개발자에게 Swagger UI와 OpenAPI JSON을 제공하고 NPM의 Basic Auth로 보호한다. 별도의 문서용 로그인 화면·회원가입·사용자 DB를 구현하지 않는다. 스펙 레포는 요구사항·계약의 원본으로 유지하고 Swagger는 배포된 API의 조회·호출 도구로 함께 사용한다.
- 문서는 `weatherhood-dev-docs.ansandy.co.kr`, 앱 API는 `weatherhood-dev-api.ansandy.co.kr`으로 분리한다. 문서 호스트에는 HTTPS와 NPM 인증을 적용하고 Swagger UI·swagger-config·OpenAPI JSON을 모두 보호한다. API 호스트에서는 Swagger·OpenAPI 경로를 차단하여 인증 우회를 막는다.
- 개발자에게 문서용 인증 정보를 제공하고 앱의 `/api/*`에는 문서용 Basic Auth를 강제하지 않는다. 인증 정보 발급·폐기는 NPM에서 관리하며 비밀번호를 Git·문서에 기록하지 않는다.
- `dev` 프로필의 `DevApiDocumentationConfiguration`이 OpenAPI 서버 주소를 HTTPS API 호스트로 고정하고, 문서 출처에서 `/api/**`의 GET만 CORS로 허용한다. 교차 출처 자격 증명은 허용하지 않는다.
- NPM 접근 목록 `weatherhood-dev-docs`는 사용자 인증과 `allow all` IP 규칙을 모두 만족해야 한다(`Satisfy Any` 끔). `Pass Auth to Host`는 끈다. IP 규칙이 비어 있으면 기본 `deny all`로 인증 전 403이 발생한다.
- 문서 프록시는 `/swagger-ui/`, `/swagger-ui.html`, `/v3/api-docs`와 하위 설정 경로, `/v3/api-docs.yaml`만 허용하고 나머지는 404로 차단한다.
- Try it out은 별도 API 호스트를 사용한다. 초기 테스트 환경에는 앱 인증·호출 제한을 적용하지 않는다. 문서 호스트를 허용하는 필요한 CORS 설정을 검증하고 문서용 Basic Auth 자격증명을 앱 API 인증으로 재사용하지 않는다.
- Actuator 상세와 기타 관리 경로는 계속 외부 차단한다. 최소 외부 상태 응답은 상세 진단 데이터와 분리한다.
- NPM 인증 동작은 도메인 연결 후 실제로 검증한다. 인증 실패 시 무인증 공개로 대체하지 않고 문서 외부 제공 완료 처리를 보류한다. 현재 알려진 인증 문제의 원인 분석은 해당 단계에서 수행한다.

| 사항 | 결정 또는 확인 시점 |
| --- | --- |

## 수용 기준

- `dev`의 검증된 커밋만 배포되고 실행 버전을 커밋·digest로 식별할 수 있다.
- PR 테스트는 GitHub 제공 러너에서 실행되고 배포 SSH 자격증명에 접근하지 못한다. 미니 PC에 self-hosted runner를 설치하지 않는다.
- 개발 브랜치 전환·IntelliJ 종료가 배포 서버에 영향을 주지 않는다.
- 배포가 겹치거나 이전 빌드가 늦게 끝나도 최신 배포를 의도치 않게 되돌리지 않는다.
- 수동 재배포는 기존 이미지 digest를 재사용한다. 롤백은 이전 정상 배포 버전과 현재 DB의 호환성을 확인한 경우에만 실행한다.
- 서버 교체 후 DB 데이터가 유지되며 배포 작업에 DB 백업·자동 초기화가 포함되지 않는다.
- 새 이미지 다운로드 후 서버만 교체하고 DB·기존 프록시은 유지한다. 실제 서비스 중단 시간을 측정하며 무중단을 성공 조건으로 요구하지 않는다.
- 빌드·다운로드·기동·마이그레이션 실패를 구분하며 안전한 복구 여부를 확인한다.
- 서버 준비 상태와 DB 연결을 5초마다 최대 2분 확인한다. 외부 공급처 장애는 준비 상태 실패로 처리하지 않으며, 외부 HTTPS 연결 실패와 내부 기동 실패를 구분한다.
- SSH 작업 종료 후에도 서버가 유지되며, 합의된 재부팅 검증에서 Ubuntu 로그인 없이 Docker·서버·PostgreSQL이 복구되는지 확인한다. 기존 서비스 정상 상태도 비교한다.
- 도메인 연결 후 외부 네트워크의 테스트 앱이 VPN 없이 HTTPS API에 접근한다.
- 외부 개발자는 합의한 접근 정책에 따라 Swagger UI·OpenAPI 명세를 볼 수 있다. DB·비공개 관리 경로는 외부 차단되고 앱 API는 초기 테스트 범위에서 인증·호출 제한 없이 접근할 수 있다.
- 문서 호스트는 인증 없이 접근할 수 없고 올바른 NPM 인증으로 UI·설정·OpenAPI JSON을 열람할 수 있다. API 호스트를 통한 문서 우회 접근은 차단되고 앱 API에 문서 인증창이 표시되지 않는다.

## 참고 및 검증

- 2026-11-17 PR #13·#14를 dev에 병합하고 GitHub-hosted runner → 비공개 GHCR → 제한된 SSH 명령으로 두 번 자동 배포했다. [배포 실행](https://github.com/kdywjs/weatherhood-server/actions/runs/44043179514)의 테스트·게시·배포·정리가 모두 성공했다. `/healthz` 외부 HTTPS 200, Weatherhood DB 중지 시 503·복구 후 200을 확인했다. 기존 서비스 13개는 유지했다.
- 전국 행정동 3,565개 적재와 마이그레이션 V1~V4를 확인했다. 서울 표본에서 현재 기온·24개 시간 키·미세먼지·일출·일몰을 확인했다. 부산·제주는 미세먼지·일출·일몰을 확인했으며 기상청 단일 요청 지연 후 다른 지역까지 일시 억제되는 문제의 보완 검증을 진행한다. 전국 부하·전체 지역 공급 검증을 완료한 것은 아니다.
